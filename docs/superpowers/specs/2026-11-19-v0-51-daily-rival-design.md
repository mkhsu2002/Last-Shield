# Last Shield：每日風暴與對手挑戰精進提案

日期：2026-11-19，America/Vancouver。
狀態：設計提案，尚待 MK 審閱核准；未修改遊戲、後端、正式版本或投稿。v0.50 已提交完成仍是目前發布基準。

## 目標與誠實界線

MK 要求持續改進，逐輪嚴格審核，直到 Delightful UX、Polish、Reddit-y、Daily Content 各達 9/10 以上。分數必須依可重現行為與實際觀察給出，不能以功能數量、測試數量或自行調高分數代替證據。沒有真實玩家或跨日觀察時，對應面向標記「未驗證」，不能宣布全部達標。9 分是內部產品品質門檻，不代表官方評分或保證得獎。

本提案先定義第一輪可獨立交付的範圍；後續每輪依前輪結果決定，不預先堆滿功能。

## 實際程式檢查

- `src/shared/game-logic.ts`：survival-6，每日 seed 改變隕石類型／方向／時間微差；波次階段循環固定，尚無玩家可讀的每日玩法主題。
- `src/client/community.ts`：已有 top ten、鄰近排名、上一名分差，但這些資訊主要在 dialog；尚無選擇一位對手並帶入下一局的流程。
- `src/client/game-ui.ts`：結果頁同時列出重玩、提交、策略分享、複製分享四個按鈕，缺少依玩家狀態排序的下一步。
- `src/server/community-service.ts`：伺服器重播、每日最高分、audit 與排名用交易更新，這是可信比分的基礎；下一版必須保留。
- 現有 0.50.0、城市／隕石美術、音效、練習回顧與私人 staging 均保留；禁止以舊版覆蓋。

## 三條路與選擇

1. **推薦：每日玩法差異＋明確對手＋結算聚焦。** 直接改善 Daily Content 與 Reddit-y，同時保留現有核心手感；成本是需要新規則版本與完整前後端同步驗證。
2. **只做視覺／文案。** 風險低，但無法解決每日內容與互動深度，不足以支持四項 9 分。
3. **立即加入公會、長期帳號成長與大型共同事件。** 社群潛力高，但引入大量資料與平衡風險，會稀釋短期迭代。延後，只有實測顯示需要時才做。

## 第一輪：每日風暴

新增純函式 dailyStorm(day)，前後端共用，日期由伺服器 session 決定。三種輪替主題：

| 主題 | 規則差異 | 玩家需要做的選擇 |
| --- | --- | --- |
| Relay Skies／接力天幕 | 接力窗口 950ms，重型核心熔解時間乘 1.15 | 多利用接力，提早處理重型威脅 |
| Crosswind／交錯疾風 | fast 類型飛行時間乘 0.92，該類熔解時間乘 0.90 | 優先處理快速威脅，避免只盯一個目標 |
| Heavy Rain／重核雨 | 非開場、非 respite 波次中可含重型第一目標，重型基本得分倍率從 1.5 改為 1.75 | 在高價值重型與較快威脅間取捨 |

選擇方式為 UTC epoch day 對 3 取餘數；有效日曆日期先驗證。UTC 連續三天保證三種不同主題，不能對 YYYYMMDD 直接取餘數而在跨月重複失衡。首三波保留原有新手節奏；練習保持獨立的固定教學規則。每局開始鎖定 day／storm，跨午夜不換規則。

開始畫面用一個短標題與一句影響說明顯示今天的風暴；明日預告只顯示下一個主題，不揭露完整序列。戰鬥 HUD 只留短主題名稱，不能增加大塊面板遮擋隕石。結果與分享顯示同一個 day／storm，避免跨日比較錯誤。

上述參數是首輪實驗值，實作後必須用模擬與實玩調整；每次調整記錄原因與結果，未通過平衡不能發布。測試需證明主題改變至少一種有效策略的相對表現，而非只有名稱變化。

## 第一輪：追分對手

- 玩家可在已有的 top／nearby 列選擇「挑戰此分數」，帶入該局的對手名稱與目標分數。沒有榜單資料時允許直接開始，不造假玩家或範例戰績。
- 預設提示使用已驗證榜單的上一個較高分數；沒有個人排名時只展示現有榜單選擇，不編造「附近對手」。自己第一名時改成挑戰個人最佳。
- 遊戲進行中不為追分輪詢後端；只展示已選分數及剩餘差距，顯示為開局目標。分數變動以結算／手動更新榜單為準，不能聲稱即時對戰。
- 超越條件為本局 score > targetScore；同分顯示追平，不能顯示擊敗。跨日、不同 rules、目標被移除時，重新選擇目標；每局追分資訊保留 day／rules，不進入重播輸入。
- 排名只在使用者提交後確認。未提交時可說「本局超過目標分數」，不能顯示「你已升到第 X 名」。
- 分享預覽含日期、風暴、分數、玩法戰績、可選心得及原貼文連結。只在有可查核榜單結果時附已確認排名；不自動留言、不標記對手、不發私訊。
- 不假定 Reddit 帖子 URL query 會傳到 WebView；第一輪沿用原生貼文連結與手動分享，不承諾未驗證的好友深連結。

## 第一輪：初次遊玩與結算

- 保留已核准的慢速 practice／結果停留／放開後 Continue；首次遊玩突出練習入口，熟悉玩家可直接開始。
- 主畫面僅保留一個主要開始動作；每日風暴說明不要求額外閱讀面板。
- 結算依狀態給一個主要下一步：可提交且尚未提交時為提交並看排名；提交完成／無登入／離線時為重玩追分。榜單與分享作次要動作，不額外增加一層結算畫面。
- 分享整合為一個含預覽、選填心得、複製與回原貼文的流程，保留剪貼簿失敗時的手動複製。
- 兩種語言、375×667／390×844／窄桌面、鍵盤、觸控、reduced-motion、靜音都逐項檢查。所有新文案包含 ARIA／錯誤／分享文字都必須對應已實作行為。
- 手機效能以實際量測為準：記錄冷啟動至可操作時間與輸入回饋延遲；目標為模擬 Fast 4G／4× CPU 降速下開始畫面 3 秒內可操作，遊戲穩定執行時輸入至可見回饋 p95 不超過 100ms。未量測不能填通過；若現有 Phaser 載入或新功能超出預算，先處理載入／初始化瓶頸，不只隱藏 bundle 警告。

## 前後端與資料契約

- 新遊戲候選使用 v0.51；實作時將 RULES_VERSION 升為 survival-7，契約升為 community-2。start／board／submit 回傳帶明確的 storm id，client 必須檢查契約／規則／storm 一致。
- Redis 新資料用新的規則 namespace；不移動、不清空、不混算 survival-6 排名。舊 v0.50 進行中局由舊套件完成；新版不假裝能接收舊規則 trace。
- 伺服器用 session day 推導 storm，不接受 client 指定規則、日期、分數或 buff。分數／主題均由同一 shared rules 重播計算。
- 無 SQL migration。仍須在 staging 與正式各自核對 client、server、permissions、rules、contract、實際 replay 與 audit；只能完整部署同一 Devvit 套件，不能只發前端。
- 優先不升級依賴。Devvit Journeys 官方要求 journey map 審核及 app allowlist；未核准前不宣稱正式 analytics 可用，也不以自建不必要追蹤繞過。真實玩家驗證可先用自願觀察與匿名彙總紀錄。

## 測試、審核與發布順序

1. 建立 baseline：指定 Node >=24.18.0，check／test／Devvit build／standalone build；保留結果，不把 baseline 當成新版證據。
2. 規則回歸：UTC 月年邊界、連續主題、首三波、練習不受影響、每個主題的 deterministic replay、不同 frame 切片一致、Overdrive／接力／損傷規則一致。
3. 平衡：至少 30 個連續日期，對相同輸入策略組合比較；不能有一種主題讓所有合理策略固定零分或無法發揮接力／超載，需記錄策略差異。
4. 契約與失敗：舊／新契約拒絕混用，跨午夜／到期／離線／匿名／交易重試／較低分／同分／移除後重送／audit 冪等均驗證。追分結果不冒充已儲存排名。
5. 私人 staging：同一 app、既有 r/last_shield_stage，真人輸入實玩及 source／CDN／server 回應交叉查核；測試分數只在 staging。正式 0.50.0 在驗證前保留。
6. 自我審核：每個問題記為阻止發布／重大／一般，先修復再重測受影響範圍。測試、平衡、文案或後端同步未通過時不合併發布。
7. 通過後照既有功能分支／PR／main 發布流程，更新同一貼文與原 Devpost；若 gameplay 改動令現影片不符，重錄並替換原投稿影片，不能把舊片當新版。

## 四項 9 分門檻與後續輪次

| 面向 | 必要證據 | 不能取代證據的項目 |
| --- | --- | --- |
| UX | 至少 5 位未玩過的自願測試者，至少 4 位無口頭教學完成 practice 並能說明按住／放開；無控制阻塞；完整記錄失敗點 | 作者自己熟練、模擬 bot |
| Polish | 雙語／尺寸／輸入／無障礙／離線與錯誤矩陣無阻止發布或重大問題；前後端與 live package 一致；分享與公開文案逐項審查 | 單純 build 或測試通過 |
| Reddit-y | 真實測試中至少 3 位玩家完成有效的追分／比較流程，並能說明他人的分數如何改變重玩目標；至少 2 位自願使用分享預覽並理解會公開什麼；不要求測試者洗留言 | 有排行榜按鈕、假造對手、代發言 |
| Daily Content | 三主題具不同策略結果；至少 3 位玩家在兩個不同 UTC 日自願回玩，能說出今日差異；模擬／跨日驗證無規則失配 | 只換日期、換 seed、預約回來但尚未發生 |

以上小樣本只是最低質性門檻，不能宣稱已證明大規模留存或病毒擴散。各項必要證據齊全後仍須嚴格評分，不能自動給 9。若第一輪未達標：第二輪優先修正觀察到的流失點；若社群面仍弱，再設計由已驗分資料驅動的共同防守目標與可選戰績卡，另立範圍及資料契約審核。每輪都產出缺陷、修正、測試與剩餘證據缺口。

## 本提案自審

- 有明確第一輪交付邊界，不以一次完成大型社群系統承諾 9 分。
- 主題影響 server replay，已列出完整部署與版本隔離；舊排行不會被新規則覆蓋。
- 目標分數與正式排名不同，已明確規定未提交／同分／跨日／資料移除行為。
- Journeys 的外部審核與真人觀察是實際依賴，沒有把缺證據當通過。
- 本文沒有宣稱已實作、已測試或已重新發布；完成狀態必須由後續驗證紀錄提供。
